/find — live build vs. design, and what has to change

Written against https://www.admitday.com/find as of Jul 30, 2026, read as content (structure and copy, not pixels). Read with design_handoff_find_screen/README.md; this file only lists deltas and the decisions made after that handoff shipped.

Two of these are blocking — /my-schools cannot be reached or populated without them.

1. Rows have no Add to list control — BLOCKING

The design's row grid is 34px 1fr 128px 96px, where the last 96px column is an Add button (1px ink outline; filled + Remove when already saved). The live rows end at the metadata line.

Without it there is no way into /my-schools from the list, and the whole saved-list screen is unreachable.

Fix: add the fourth column. Optimistic toggle, localStorage until auth, header count increments in the same tick. Same two states as the button on /school, so the control is recognisable across screens.

2. The header carries no saved count, and nav item three is stale — BLOCKING

Live: Home / My Schools / Readiness.
Design: Find / My Schools + mono saved count in accent / Checklist.

Three separate changes:

  • Home → Find. The route is the product's core screen, not a homepage. If a marketing landing page needs a nav slot, it goes on the wordmark, which already links to /.
  • Mono saved count on My Schools, in accent, at 12.5px. This is the only feedback that Add worked, and it's the entry point to /my-schools.
  • Readiness → Checklist. Decided while designing /my-schools: requirements and deadlines live on that screen, and "Readiness" implied a score, which the product does not produce. Rename everywhere.

3. Rows are missing the two fields the saved list compares on

Live rows show Borough · Track. The design shows Neighborhood · Track · N students (or DBN) plus a stat column: applicants per seat in mono.

/my-schools puts applicants-per-seat and neighborhood side by side on every saved school, because that is how a family tells its list apart. If /find doesn't surface the ratio, the only selectivity signal in the product is two clicks deep — the specific trust failure the /school stats grid was built to fix. A parent should not be able to add twelve schools without once seeing how selective any of them are.

Fix: add the stat column (applicants_per_seat, mono 16px over a 10.5px uppercase faint label) and put neighborhood in the metadata line. Omit the stat cell entirely when the DOE didn't publish it — never —, never 0. Same rule as /school and /my-schools.

4. Rows don't appear to link to /school/[dbn]

School names read as plain text. They are the primary navigation into the detail view, which is designed and handed off.

Fix: name is a link; whole row is hoverable (surface-2), name and Add are the only click targets.

5. All 457 schools render as one flat list

No result-count band, no active-filter summary, no paging.

The design has a results count band (16px 36px, surface-2, border-bottom: 1px rule): left, mono count + the active filters named in plain language (31 matches in Brooklyn + Queens, Screened); right, mono uppercase SORTED BY FIT. And a footer band with 26 more matches — paginate or lazy-load.

Naming the filters is load-bearing in two places downstream: /school's back band echoes that exact string (‹ Back to 31 matches · Brooklyn + Queens, Screened), and /my-schools shows the same criteria as chips. All three read one source.

Fix: add both bands. Cap the initial render (~25 rows).

6. The ask box is a separate field below the filters, with no chip mechanic

Live: Interests, then Ask, as two more fields in the filter stack, with the note "Filters narrow the list. The ask box below just annotates it — nothing gets removed."

The design puts the ask in the right column as a command bar with a mono › prompt and a square accent submit, and — the important part — renders every signal it extracts as an individually removable accent chip under an APPLIED eyebrow.

That copy line is honest about the current behavior, but it's describing a workaround: if the ask only annotates, the system has inferred something it won't show and can't be corrected. The chips are the trust mechanic, and they're also the input for two downstream screens: /school's MATCHED YOUR ASK accent chips, and /my-schools' SELECTION CRITERIA strip. Neither has an input until the ask returns structured signals.

Fix, in order:
1. The ask endpoint returns the extracted signals as structured data ({ id, label, kind }), not just prose. If this needs API work, it is the first thing to do — everything else here is layout.
2. Render them as chips with a trailing ×. Removing one re-runs matching locally, without re-calling the model.
3. Move the ask out of the filter stack into the right column above the results.
4. Fold Interests into it — a free-text interest is an ask signal, not a fourth filter group.

7. Filter rail — mostly right, two gaps

Borough, Admissions track and Size are all present with the right options, and Reset filters exists. Missing from the content:

  • Per-track match counts — the design shows a mono count of matching schools on each track row, and N selected in accent on the Borough group label. Counts are what make a deterministic filter feel deterministic.
  • Size as a segmented control — 4 equal cells in one 1px border box, selected cell ink-filled. Live it reads as a list of four options. Behaviorally the same, visually a different primitive.
  • Confirm the rail is 316px with border-right: 1px solid rule. That measure is now shared by /school's info rail and /my-schools' composition rail — it's the product's spine.

Zoned and Educational Option are in the live data, so keep both in the track list.

8. Filter state must be in the URL

Can't be confirmed from content, so flagging it: the design requires filter state as query params. /school's back band and /my-schools' Edit criteria link both serialize back to a filtered /find. If state is component-only, both break on refresh or share.

9. Footer disclaimer — keep, and reword slightly

The live footer is doing the right job and says more than the design asked for. Two notes:

  • Keep the MySchools link and the "no tool can guarantee an offer" framing. That is the trust story.
  • The DOE-randomness sentence is good but long for a persistent band. The design's version — "Requirements and deadlines from DOE data · confirm at MySchools before you submit" — is the standing line; the fuller paragraph belongs on an About or methodology page, or in the sign-up flow. /my-schools follows the short pattern (two 13px faint lines).

Order of work

  1. Add to list on rows + live saved count in the header. (Unblocks /my-schools.)
  2. Readiness → Checklist; Home → Find.
  3. Row links to /school/[dbn]; applicants-per-seat stat column; neighborhood in the metadata line.
  4. Filter state in the URL.
  5. Ask returns structured signals → chip bar → move the ask into the right column, absorb Interests.
  6. Results count band with named filters, footer paging.
  7. Rail polish: per-track counts, N selected, segmented Size control.

1–3 are enough to make /my-schools real. 5 is what makes /school and /my-schools show the family their own words back.

Not a delta, but worth stating

Nothing in the live content suggests a derived score, rating, or admissions prediction anywhere. That's the hardest constraint in this product to hold, and it's being held. Keep it that way: no "reach/target/likely", no fit percentage, no selectivity rating — only DOE values, published as given.
