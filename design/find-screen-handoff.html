Handoff: Admit Day — /find (unified filter + ask surface)

Overview

This is the visual direction for Admit Day's core screen: the unified /find surface that replaces the separate /list → /requirements filter flow and /chat (roadmap item #99). One screen: a deterministic filter rail, a natural-language ask box whose inferred signals appear as removable chips, and one ranked list of schools with real per-school requirements and stats.

Target codebase: Next.js 14 App Router + React + Tailwind CSS, Vercel Postgres. Data is one schools (dbn TEXT PRIMARY KEY, data JSONB) row per school, loaded via lib/load-schools.ts → getAllSchools().

About the design files

The files in this bundle are design references created in HTML — prototypes showing intended look and layout, not production code to copy. The task is to recreate this design in the existing Next.js + Tailwind codebase using its established patterns (App Router server components for data, Tailwind classes rather than inline styles, existing lib/school-list-utils.ts filtering helpers). Do not paste the HTML in.

All content in the mock is placeholder — school names, rationales, and stats are illustrative. Real values come from Postgres.

Fidelity

High-fidelity. Colors, typography, spacing, and layout are final and should be matched closely. Interactions are indicated but not implemented — the mock is static.

Geometry

  • Radius: 0 everywhere. No rounded corners on chips, buttons, inputs, or panels. This is load-bearing for the editorial feel.
  • Shadows: none inside the UI. (The mock's outer drop shadow is presentation only — do not implement.)
  • Separation is done with 1px rules, not cards or shadows.
  • Design width 1120px. Spacing steps used: 6, 8, 10, 12, 14, 16, 18, 22, 26, 28, 30, 34, 36px.

Right column

Interactions & behavior

  • Filters — client state; each change re-runs deterministic filtering (lib/school-list-utils.ts) and updates counts. Filter state belongs in the URL as query params so a list is linkable (prerequisite for the shareable-output roadmap item).
  • Ask submit — POST to the existing RAG route. Response must return (a) the extracted exact signals so they can be rendered as chips, (b) the ranked dbn list, (c) per-school rationale strings, and (d) the one-sentence summary. Rate limiting already exists per-IP; surface a plain-language message when it trips.
  • Chip removal — removing an ask-derived chip re-runs matching without re-calling the LLM: the extracted signals are structured filters once returned. Only a new ask hits the model.
  • Add — optimistic toggle; button flips to an added/Remove state and the header count increments. Persist to localStorage until auth lands.
  • Sort — Sorted by fit is a dropdown: Fit, Applicants per seat (low→high), Size, Name.
  • Loading — the ask box gets a determinate-feeling pending state (disable submit, show a mono status line in the band); results keep the previous list visible rather than emptying. Do not use skeleton cards; rules-and-rows layouts flicker badly.
  • Empty — when filters return nothing, keep the rail and band and show one line in the results area naming which filter to loosen. When getAllSchools() returns [] (DB error), keep the existing empty-state banner.
  • Hover — rows get surface-2 background; Add inverts (fill ink, white text); chips show a stronger ×. All transitions 120ms ease-out. No transforms, no lift.
  • Responsive — below ~900px the 316px rail collapses to a Filters disclosure above the ask box, and result rows stack: name/metadata/rationale, then stats in a horizontal row, then a full-width Add. The 1120px layout must never be allowed to squeeze — below design width, reflow, don't compress.

State

filters:  { boroughs: string[]; tracks: string[]; size: 'any'|'small'|'medium'|'large' }
ask:      { query: string; status: 'idle'|'pending'|'error'; signals: Signal[]; summary: string }
results:  { dbns: string[]; rationales: Record<string,string>; total: number; shown: number }
saved:    string[]   // dbns, localStorage until auth
sort:     'fit'|'apps_per_seat'|'size'|'name'

Signal = { id: string; label: string; source: 'user'|'ask'; kind: 'borough'|'track'|'interest'|'sport'|'geo' } — source drives chip styling; kind drives how it is applied in filtering.

Do you need a design system?

Not a component library — but yes to a token layer, and it's about a day of work:

  1. Put the colors above in tailwind.config.ts as named tokens. Never write a raw hex in a component.
  2. Load the four fonts via next/font/google and expose them as font-display (Space Grotesk), font-sans (Libre Franklin), font-mono (JetBrains Mono), font-wordmark (Newsreader italic).
  3. Set global defaults: rounded-none, no shadows, text-wrap: pretty on body copy.
  4. Extract exactly five primitives — Chip (variants: set / inferred / unselected / add), SegmentedControl, Button (variants: primary / outline), StatBlock, SchoolRow. That's the whole system. Everything else is layout.

Skip anything more until there is a second screen. The tokens are what stop drift; a component library this early just slows you down.

What happens next

  1. Land the token layer and the five primitives.
  2. Build /find as the new unified route behind the existing filter + RAG endpoints, with filter state in the URL. Delete /list, /requirements and /chat once it works — per the roadmap there are no users to protect yet.
  3. Make sure the ask response returns extracted signals as structured data. If it doesn't, the chip mechanic — the whole reason this screen works — cannot be built. Do this first if it needs API changes.
  4. Then the shareable list / PDF export, which this layout is deliberately built for: rules-and-rows on white prints cleanly and screenshots legibly.

Not designed yet: the school detail view, the saved-list view, and the landing page. Ask for them before improvising — they should follow the same three-faces / no-radius / one-accent rules.

Assets

None. No images, icons, or illustrations — the only graphic elements are the 9px accent dot in the wordmark and text glyphs (›, ✓, ×, ⌄). Replace the glyphs with your icon set if you already have one; keep them at text size and weight.
